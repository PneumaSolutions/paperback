# Scanning: developer notes

Notes for reviewing File > Scan Document: how it's built, where it departs from the spec and why, how Quin's answers of 2026-11-21 were applied, a security review, what was tested, and how the second independent review was resolved. The user guide section is "Scanning documents" in `readme.md`. (This file isn't a user guide: the docs build only picks up `readme*.md`.)

## How it's built

* `crates/paperback/src/scanning/scanner.rs`: the scanner interface, a thin layer over [pagescan](https://github.com/PneumaSolutions/pagescan) on all three platforms. `Scanner` lists scanners with their sources, scans pages as images (each page handed over as soon as it's scanned), and cancels. `SystemScanner` is pagescan; `fake::FakeScanner`, built only for tests, hands back scripted pages. It was a crate of its own, `paperback-scan`, until SANE moved into pagescan left it with no platform code, and only the desktop app uses it. Sources are what the reader picks: flatbed, feeder (one side), feeder (both sides).
* pagescan (Pneuma's scanner library, MIT): WIA 2.0 with a WIA 1.0 fallback on Windows, ImageCaptureCore on macOS, SANE on Linux, loaded at run time with `libloading`. Paperback uses `scan_with_pages`, `ErrorKind::SaneMissing` and `ScanOptions::app_events`, added for Paperback on pagescan's `paperback-api` branch. `scan_with_pages` streams: each page is handed over by value as soon as it's decoded and isn't kept in the outcome, and its 4 GB cap counts only pages not yet handed over. The library holds one page at a time on Linux and macOS; on Windows the driver's thread decodes ahead, but waits once two pages are waiting for Paperback. On Windows and Linux the driver runs on a thread of its own, and pagescan gives up on it 30 seconds after the timeout or a cancel, keeping the pages so far, so a hung driver can't hold a run for good.
* `paperback-core`:
  * `scan::archive`: the scanned document, a comic book archive (`.cbz`) of PNG pages with a `ComicInfo.xml` that names it and marks it with `<ScanInformation>Paperback</ScanInformation>`. A page is appended in place (departure 5); an append that fails puts the old central directory back, so the archive is as it was. The first page, a rescan's replacement and Save Scan As write a whole new archive beside the old one and rename it over it. `is_scan` tells Paperback's scans from other comics, so their OCR lines are joined into paragraphs like a PDF's.
  * The existing comic parser and renderer read it: every page is an OCR placeholder with the `ImageOnlyPage` marker, so Recognize Current Page, Batch OCR and the saved-pages store work on it unchanged. The comic parser now gives each page an anchor, so a reload of an archive that grew keeps the caret on its page.
  * `scan::check`: the feedback checks. Blank (share of ink, ignoring a 2% border where the lid and paper edges leave shadows), plausible words (to tell a page that reads from one upside down or sideways), the best turn, little text, and words against an edge.
* The desktop app:
  * `scanning/`: what is remembered per scanner, what happens to a page (`pages::read`: OCR, then the other orientations when the page reads poorly), every message the run says, and `store` (the scans-in-progress folder, Save Scan As, discarding, and the sweep at start).
  * `ui/dialogs/scan.rs`: the Scan Document dialog and the Scanning window.
  * `ui/scan_session.rs`: the run itself. A scanner thread hands pages to an OCR thread through a queue three pages deep (the scanner waits when OCR is behind). The OCR thread checks and reads each page in order, adds it to the archive (it's the archive's only writer, and numbers each page and its text from the archive's own count), and posts what it did to the UI thread with `when_unlocked`. The UI thread owns the tab and speaks; it never writes the archive. A watchdog thread ends a run whose scanner never returns.
  * `ui/document_manager/scan.rs`: opens the scan after its first page, and installs re-reads that were parsed off the UI thread.

### The flow

1. File > Scan Document. The first time, the scanners are listed behind a cancellable progress dialog. After that, the last scanner is offered without asking the system, with Find Other Scanners in the dialog.
2. Source, color and resolution default to the flatbed (or the one-sided feeder on a scanner without one), grayscale, 300 DPI. They're remembered per scanner, as one JSON value under the app setting `scanners`, because scanner IDs contain backslashes and braces.
3. The Scanning window stays open: a status line that's announced (a UIA notification on Windows), and only the buttons that apply right now.
4. Flatbed: scan, open the document after the first page, read the page and say "Page N: W words." (said once the buttons have changed, so the focus moving to Scan Next Page doesn't cut it off). Then Enter scans the next page and Escape finishes. A page that may not be lined up is announced and gets a Rescan button beside Scan Next Page, which keeps Enter; a blank page stops with Rescan or Skip. Feeder: the first page is announced as its text is read, then "N pages so far" at most every 5 seconds, then a summary with the notes about particular pages (turned, blank, out of line, unreadable; the first five, then a count), then Enter scans more into the same document. Escape while a feeder is scanning asks before stopping it.
5. A page is read (and turned if need be) before it goes into the archive, so it's added once, with its text. The document opens after the first page has been read, and later pages appear as they're read: within a second or so while the Scanning window is open, and all at once at the end of the run after it's closed (see departure 5).

## Departures from the spec, and why

1. **WIA through classic COM, not Windows.Devices.Scanners.** pagescan uses WIA 2.0 (`IWiaDevMgr2`) with a WIA 1.0 fallback. On our test laptop, the HP Color LaserJet Pro MFP 3301's network eSCL device only appeared through WIA 1.0, which the WinRT API can't reach. This was already in Mike's reply to Quin.
2. **SANE lives in pagescan.** That was Quin's answer. Paperback's scanner module has no platform code of its own.
3. **Scans are comic book archives.** Quin's answer. `paperback-formats` and the parsers are untouched; the archive is written with a `ComicInfo.xml` (title, and `ScanInformation` = Paperback), which other comic readers show and which tells Paperback to join OCR lines into paragraphs (`archive::is_scan`, checked in `joins_lines`). The OCR text is stored inside the archive: each page's lines and word boxes go in a `page-0001.ocr` entry beside `page-0001.png`, in the saved-pages store's own format (`ocr::encode_pages`), written in the same append as the image, so each page is still written once. A rescan replaces both. Opening a scan reads the archive's text first and lays anything in the saved-pages store (Recognize Current Page or Batch OCR since) over it (`restore_recognized`). Comic readers, and Paperback's comic parser, skip entries that aren't images. So a scan is portable: copied or shared, it opens with its text.
4. **Scans in progress, Save Scan As, and clearing.** Quin's answer: the `scans` folder (in Paperback's settings folder, 0700 on Unix) is for work in progress, named "Scan", "Scan 2", and so on. File > Save Scan As (no shortcut) writes a copy where the reader chooses, titled by its file name, with its text, and the saved copy replaces the in-progress one in its tab at the same position. What I chose for old ones: closing an unsaved scan asks Save / Don't Save / Cancel, and Don't Save deletes the archive, its text and its Recent Documents entry. Nothing else deletes a scan unasked (after Quin's second review). A scan left open at exit comes back with "reopen documents". At start, once restoring is done (or 1.5 s after the window comes up, when restoring is off), any scan in progress that no tab has open is offered in a small dialog: "Paperback found 2 unsaved scans from last time. Open them now?" with Open (the default), Delete... (which confirms) and Keep for Later (Escape; asked again next start). That's one question, at a predictable moment, with the safe choice on Escape, which I judged least surprising for a screen-reader user; opening them silently would leave unexplained tabs. Only a file with not one complete page, and stray temporary files, are cleared; a file that couldn't be read or repaired just now (locked, a read error, a full disk) is kept and mentioned in the question. While a run is still adding pages to a scan, Save Scan As and closing its tab are refused with a spoken reason, and quitting asks first, so no page is lost and nothing is written to a scan that's gone.
4a. **Recovering a scan cut short.** An append rewrites only the central directory, so a crash during one leaves every earlier page intact. When a scan in progress doesn't open (at restore, or when unsaved scans are gathered), `archive::repair` walks the local file headers from the start, keeping each entry while it's whole: sizes in the header (no data descriptor), data present, inflated if deflated (an earlier build deflated `ComicInfo.xml`), non-empty, and matching its CRC-32. It stops at the first entry that fails, or at a gap in the page numbering, and writes a new archive with what it kept (a temporary file renamed over). One entry is in memory at a time. At start the repair runs behind a progress window, off the UI thread; for a scan reopened with the other documents it runs as the tab is restored. A header whose sizes were never filled in (the writer stops before going back to them) is caught by the empty-data check. A recovered scan is announced ("Scan 2 was cut short when Paperback closed; its complete pages have been recovered.", or in the start-up question). Tests cut archives short in the middle of a page, in the central directory, and after an unfinished header.
5. **Writing and re-reading, sized for long runs.** A page is OCR'd (and turned) before it's added, so each page reaches the archive once, already the right way up, with its text: one append in place (`ZipWriter::new_append`, the page plus a new central directory) and one fsync. Only the first page, a rescan's replacement and Save Scan As write a whole archive (to a temporary file, renamed over). The archive keeps its own page count, so adding a page reads only its central directory. All of this happens on the OCR thread, not the UI thread. The tab shows new pages by re-parsing (the same parse as F5), with each page's text coming from the archive itself and anything recognized since (in the saved-pages store, keyed by the archive's contents) laid over it; when a page changes the contents, that store file is carried over to the new key. The parse runs on a thread of its own, holding the archive's lock so it never reads a page half written, and only the result is installed on the UI thread. That re-read is coalesced: the first page opens the document at once; while the Scanning window is open, pages arriving within 0.8 s (a little longer as the scan grows) share one re-read, and only one parse runs at a time; once the window is closed (the reader may be reading), pages still being read are added in a single re-read when the run ends, so the text under the caret isn't replaced mid-reading. Each page has an anchor, so a re-read keeps the caret on its page. A failed append puts the archive back as it was; a crash mid-append can leave the scan in progress unreadable until it's repaired (departure 4a); a saved scan is never appended to. Pages travel from the scanner thread to the OCR thread as PNG (encoded in the scanner library's callback), through a queue three pages deep: a feeder faster than OCR waits rather than piling up pages; that PNG is what's stored unless the page was turned.
6. **OCR for scanned pages doesn't go through the Batch OCR pool.** The run needs each page's result in order, as it arrives, for the announcements and checks. The pool works from a file and a list of page numbers. The run reuses the same engine call (`crate::ocr::recognize_lines`), the same saved-pages store, and the same restore path. Batch OCR and Recognize Current Page work on a scan afterwards.
7. **Rescan without stopping, for pages out of line.** Quin's answer. A page that's upside down or sideways is turned and kept automatically, with a brief note ("Page 3 was upside down; corrected."). A page with very little text or text touching an edge is announced, and on the flatbed a Rescan button appears beside Scan Next Page: Enter still goes on, and Rescan scans the page again in its place. A blank flatbed page (probably face down) still stops with Rescan or Skip, for now, as Quin asked. A feeder can't take one page back, so there these are announced only. From the feeder, blank pages follow the same opt-in Skip blank pages setting as two-sided scanning (decided after Quin's review): off by default, a blank page is kept and announced as looking blank, since a page with only a faint signature could otherwise be lost; on, pages without text are left out and counted.
8. **No default shortcuts** for Scan Document or Save Scan As, as Quin asked. They can be set in Customize Keyboard Shortcuts.
9. **macOS isn't tested.** ImageCaptureCore delivers its callbacks on the main thread, with no way to ask for another thread or queue, so there the scan runs on the UI thread (`Scanner::needs_main_thread`), and pagescan pumps the run loop. Pumping the run loop doesn't dispatch window events, so Paperback sets pagescan's `ScanOptions::app_events`: pagescan hands pending AppKit events to the app while it waits, the Scanning window keeps answering, and Stop works (the main window is disabled by the modal Scanning window, so nothing else can start). Pages are still read and saved on the OCR thread, but the document may only update when the scan returns. pagescan's macOS backend itself hasn't run on hardware yet.
10. **Searchable PDF is a follow-up,** as agreed. Plain text and Markdown export work now.

### Skipping blank pages is opt-in

Mike proposed skipping blank sides for two-sided scanning; Quin made it opt-in, since OCR finds no words in photos, signatures or handwriting, and after his review it covers the one-sided feeder too.

* "Document feeder, one side" (listed first, the feeder's default) and "Document feeder, both sides" keep every page or side by default. The one-sided feeder announces a blank page as looking blank, since the stack may be face down.
* "Skip blank pages" (a checkbox for either feeder source, off unless chosen, remembered per scanner) leaves out blank pages or sides. A page with no ink at all is dropped without OCR. A page with ink is read; it's kept if OCR finds real text (at least 3 plausible words, characters or groups of figures, see below, after trying the other orientations). If it doesn't, the page is read once more mirrored (left to right, and top to bottom): show-through is the other side's print seen from behind, so it reads only mirrored, and then the side is dropped. Anything else with ink (a photo, a signature, handwriting, a table of figures, a script the OCR language doesn't cover) is kept and announced as "no text found", and after three such pages in a row Paperback says once that the OCR language might not match. With no OCR engine, the ink check alone decides. A face-down sheet's printed side arrives second and upside down, and is turned. The end sums up ("5 sheets, 7 pages, 3 blank sides skipped", or for one side "Scanned 7 pages. 2 blank pages left out...").
* On the flatbed nothing changes: a blank page means "may be face down; turn it over and Rescan".

Code: `pages::Mode`, `pages::is_blank_side`, `scan_session::sort_page`. Tests run fake feeders through each mode (`ui::scan_session::tests`).

### Scripts written without spaces, checked against real OCR

Windows OCR and Tesseract report each Chinese or Japanese character (and each Thai, Lao, Khmer or Burmese one) as its own word, so counting words with two or more letters scored such pages zero: every page tried all four orientations, a turn was never chosen, skipping dropped every side, and the count announced was of characters called words. `scan::check` counts characters of Han, Hiragana, Katakana, Thai, Lao, Khmer and Myanmar one by one as plausible text, and the announcement says "Page 3: 512 characters." when such characters outnumber words (`TextAmount`). Korean is written with spaces and counts by the word.

Real Windows OCR then showed that counting every Han character isn't enough. On the HP, with the zh-Hans-CN recognizer installed, one page of Chinese read as 195 characters the right way up and, upside down, as 27 real but unrelated characters (圭 園 寻 腰 孑 杲 兽 畀 碧 鞠 旱 鞋 壬 ...). 27 is over the turning threshold, so the page would have stayed upside down. So a Han character now counts as plausible only if it's among about 540 common characters (`scan::common_han`, simplified plus the commonest traditional forms; kana and the other scripts still count every character). Function words and everyday vocabulary make up most of real text, and a misreading lands on them only by chance. With the same real OCR output: upside down scores 7 (turn tried, Half chosen, scoring 180), the right way up scores 180 (kept), and sideways scores 6 (Quarter chosen). The OCR output itself is a test (`real_windows_ocr_of_upside_down_chinese_asks_for_a_turn_and_gets_it`). Windows' OCR API gives no confidence, so that signal wasn't available. Japanese wasn't tried on real OCR, since only the Chinese recognizer was installed. The thresholds (25 to try turning, 40 to stop trying, 3 for a side with text, 15 for little text) apply to words and characters alike.

## Security review

Scope: the scanner module, the new paperback-core modules (`scan::*`, `parser::scan`), the desktop scanning code, and pagescan's Linux backend and `scan_with_pages`. pagescan's own review is in its `SECURITY_REVIEW.md` (findings 24 and 25 cover the SANE backend).

* **Image data from drivers is untrusted.** pagescan bounds every page before decoding it: 1 GB of driver data, 250 megapixels, 500 pages, 4 GB per scan. Dimensions are checked before pixels are allocated, on all three backends. SANE frame parameters are validated before allocation, and `sane_read` lengths are clamped. Paperback receives decoded `DynamicImage`s, so it never decodes driver bytes itself. The checks shrink a page to 1000 pixels before looking at it. OCR gets at most the engine's own maximum dimension.
* **Opening a scan from elsewhere** is opening a CBZ, through the existing comic path. Its `page-*.ocr` entries are parsed as the saved-pages JSON lines: only entries named for a page the archive has, numbered by the name, at most 16 MB each and 256 MB in all, with unreadable lines skipped.
* **Repairing** reads only files in the scans folder. The header walk checks each entry's claimed size against the file's length before reading it (no read can run past the file, and nothing larger than the file is allocated), stops at anything it doesn't expect (data descriptors, Zip64 sizes, unknown methods), inflates at most the declared size plus one byte, and requires each entry's CRC-32 to match. The parser reads only entry names. Pages are decoded when they're OCR'd, by `image::load_from_memory`, with the image crate's default limits. That's an existing property of the comic path, not new here. A tighter limit on decoded page size for both would be a reasonable follow-up.
* **Temporary and saved files.** Archive rewrites (the first page, a rescan, repair, Save Scan As) use `tempfile` in the archive's own folder (created 0600 on Unix), are synced, then renamed over the archive; a crash during one leaves at most a `.scan-*.tmp` file. Appends are written in place: one that fails puts the old central directory back and cuts off what it wrote, and a crash during one can leave the scan in progress without a central directory, which the repair at the next start recovers up to the last complete page. The scans folder is set to 0700 on Unix. On Windows it inherits the per-user ACL of the settings folder. Entry names are fixed (`page-0001.png`, `ComicInfo.xml`, whose title is XML-escaped). `is_scan` reads at most 64 KB of a `ComicInfo.xml`. The archive's file name comes from a translated string, with characters a file system refuses replaced, and never contains a path separator. Existing files in the scans folder are never overwritten: "Scan 2", "Scan 3" and so on. Save Scan As overwrites only after the file picker's own confirmation, or Paperback's when `.cbz` was added to the name typed, and never saves into the scans folder. Deleting is limited to files directly in the scans folder (compared after canonicalizing), so a saved scan elsewhere is never deleted. The OCR text store is written only on the UI thread, so the run and Batch OCR never write it at once.
* **SANE through `libloading`** (in pagescan): only `libsane.so.1`, then `libsane.so`, found by the dynamic linker. It must export all eleven SANE entry points. It's never unloaded, because backends such as sane-airscan keep threads. All calls but `sane_cancel` are serialized under one lock. A cancel only sets a flag that the scan thread checks between reads; `sane_cancel` is called from another thread only as a fallback 5 seconds later (the SANE standard allows it, but many backends aren't written for it), and never on a closed handle. Numeric options are used only if they are INT or FIXED with a size the buffer holds. Strings and lists from backends are bounded and copied out.
* **No network calls.** Neither Paperback's scanning code nor pagescan opens a socket. Network scanners are reached by the operating system's own drivers (WIA's eSCL driver, ImageCaptureCore, sane-airscan), as configured by the system. The simulated eSCL scanner in pagescan's CI binds to 127.0.0.1 and isn't shipped.
* **Settings.** The remembered-scanner JSON is parsed defensively. Unknown sources, out-of-range resolutions and damaged JSON fall back to defaults, and a missing last scanner means picking again.
* **Threads.** Only owned data crosses threads: images, PNG bytes, recognized lines, a parsed document. No wx object leaves the UI thread. The archive is shared behind a mutex: the OCR thread writes it, and the re-read parse and the first open lock it to read it whole. A run that outlives its window keeps adding pages and speaks once, with the final count, when it ends; the tab can't be closed or saved over until then.

## Building

* pagescan is a git dependency at a fixed revision, because it isn't on crates.io yet. **Its repository is private for now, so CI on the public fork can't fetch it, and every job will fail at dependency resolution until it's public.** Locally, either let cargo fetch it with your GitHub credentials (`CARGO_NET_GIT_FETCH_WITH_CLI=true` with `gh auth setup-git`), or point it at a checkout from a `.cargo/config.toml` that you don't commit:

  ```toml
  [patch."https://github.com/PneumaSolutions/pagescan"]
  pagescan = { path = "../pagescan" }
  ```

## Second independent review (2026-11-21) and how it was resolved

An independent review by reading of pagescan (`paperback-api`) and this branch found no critical issues, 4 high, 10 medium and 12 low. Each was checked against the code first; all were confirmed as described (M10, L11 and L12 were marked "suspected" by the reviewer and depend on drivers). Quin's agreed design is unchanged: CBZ with `page-NNNN.ocr` entries, appending in place, opt-in Skip blank pages, the Scanning window, and the start-up question about unsaved scans.

High:

1. **Pages lost after Done, and scanning locked up.** Confirmed: `apply` returned early for every event once the archive was gone, including `Ended`, and nothing checked for a live run in Save Scan As, closing the tab or quitting. Fixed: a run now lasts until the OCR thread has finished with every page the scanner handed over, and `Ended` is never swallowed. While a run owns the archive, Save Scan As and closing its tab are refused with a spoken reason ("This scan is still being read..."), and quitting asks first. Done says "Finishing the scan. Paperback will say when the document is complete." and the final count is said once at the end. The queue to OCR is now three pages deep (M2), so after Done at most a few pages are left to read. Tests: `a_scanner_that_never_returns_is_given_up_on`, plus the run tests below.
2. **Recovery deleted a scan whenever repair failed.** Confirmed: `recover` turned every error into `None`, which `unsaved_in` deleted. Fixed: `archive::repair` returns `Repair::NothingToRecover` apart from errors, and `store::recover` returns `Recovery::{Intact, Repaired, Unreadable, Empty}`. Only `Empty` (truly no complete page) is deleted; `Unreadable` is kept and mentioned in the start-up question ("could not be opened just now; it is kept"), and a scan reopened with the other documents that can't be repaired is kept and announced. Tests: `a_scan_that_cannot_be_repaired_just_now_is_kept_not_deleted`, `a_repair_that_cannot_write_its_copy_keeps_the_scan`, `a_repair_that_cannot_read_the_file_is_an_error_not_nothing_to_recover`.
3. **A failed append damaged the archive, kept the feeder going and misaligned text.** Confirmed (zip's `Drop` does try to finalize; the new test shows it). Fixed: `append` keeps the old central directory and, on any error, writes it back and cuts the file to its old length, so the archive is exactly as it was and the page isn't counted. The OCR thread is now the archive's only writer and numbers each page and its `.ocr` text from the archive's own count, so text and image can't drift apart. On the first storage failure the scanner is cancelled, later pages are ignored, and the reader hears once "Page N could not be saved: reason. Scanning stopped. The N pages before it are safe." A late page for a deleted scan is refused rather than writing a new archive. Tests: `an_append_that_fails_partway_leaves_the_archive_as_it_was`, `a_deleted_scan_is_not_brought_back_by_a_late_page`, `a_page_that_cannot_be_saved_stops_the_scanner_and_is_said_once`, `pages_continue_the_archive_s_numbering_and_text_stays_with_its_page`. Checking free space before a run wasn't added: the undo makes a full disk safe whenever it happens.
